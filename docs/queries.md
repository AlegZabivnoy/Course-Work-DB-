# Аналітичні SQL-запити

Аналітичні запити дозволяють оцінювати ефективність
роботи сервісного центру та магазину запчастин,
визначати популярні товари й аналізувати динаміку
продажів.

## 1. Топ-3 запчастини за виручкою в кожній категорії

### Бізнес-питання

Які запчастини приносять найбільшу виручку в межах
кожної категорії та на які товари варто звернути
увагу під час планування закупівель?

### API

`GET /analytics/top-parts`

### Реалізація

`src/repositories/analytics.repository.ts`

Функція: `getTopPartsByCategory()`

### SQL-запит

```sql
WITH revenue AS (
    SELECT p.part_type::text AS category,
           p.id AS part_id,
           p.name,
           SUM(oi.quantity * oi.unit_price) AS total_revenue,
           ROW_NUMBER() OVER (
               PARTITION BY p.part_type
               ORDER BY SUM(oi.quantity * oi.unit_price) DESC
           )::int AS position
    FROM shop_order_items oi
    JOIN shop_orders o ON o.id = oi.order_id
    JOIN parts p ON p.id = oi.part_id
    WHERE o.status <> 'cancelled'
    GROUP BY p.part_type, p.id, p.name
)
SELECT category,
       part_id AS "partId",
       name,
       total_revenue AS "totalRevenue",
       position
FROM revenue
WHERE position <= 3
ORDER BY category, position;
```

### Пояснення

1. JOIN об'єднує три таблиці: shop_order_items,
   shop_orders та parts.
2. WHERE виключає скасовані замовлення.
3. GROUP BY групує позиції замовлень за запчастинами
   та їхніми категоріями.
4. SUM обчислює загальну вартість проданих позицій
   як добуток кількості та ціни на момент замовлення.
5. CTE revenue формує проміжний результат
   із розрахованими показниками.
6. ROW_NUMBER присвоює кожній запчастині позицію
   в межах її категорії.
7. PARTITION BY розділяє рейтинг за категоріями.
8. WHERE position <= 3 залишає лише три найкращі
   запчастини кожної категорії.
9. ORDER BY сортує результат за категорією
   та позицією в рейтингу.

Для категорій, у яких менше трьох запчастин
із замовленнями, повертається менше трьох рядків.

Якщо декілька запчастин мають однакову виручку,
їхній взаємний порядок не гарантовано.

## 2. Продажі магазину за місяцями

### Бізнес-питання

Як змінюється обсяг продажів магазину запчастин
від місяця до місяця та в які періоди спостерігається
зростання або зниження продажів?

### API

`GET /analytics/monthly-sales`

### Реалізація

`src/repositories/analytics.repository.ts`

Функція: `getMonthlySales()`

### SQL-запит

```sql
WITH monthly AS (
    SELECT date_trunc('month', o.created_at) AS month,
           SUM(oi.quantity * oi.unit_price) AS revenue
    FROM shop_orders o
    JOIN shop_order_items oi ON oi.order_id = o.id
    WHERE o.status <> 'cancelled'
    GROUP BY date_trunc('month', o.created_at)
)
SELECT month,
       revenue,
       revenue - LAG(revenue) OVER (
           ORDER BY month
       ) AS "changeFromPreviousMonth"
FROM monthly
ORDER BY month;
```

### Пояснення

1. JOIN об'єднує замовлення магазину
   та їхні товарні позиції.
2. WHERE виключає скасовані замовлення.
3. DATE_TRUNC приводить дату створення замовлення
   до початку відповідного місяця.
4. GROUP BY групує замовлення за місяцями.
5. SUM обчислює загальну вартість замовлень
   за кожен місяць.
6. CTE monthly формує проміжну таблицю
   з місячними показниками.
7. LAG отримує значення виручки попереднього
   рядка в хронологічному порядку.
8. Віднімання попереднього значення від поточного
   визначає абсолютну зміну продажів.
9. ORDER BY сортує результат за місяцями.

Для першого місяця значення зміни дорівнює NULL,
оскільки попередній період відсутній.

### Приклад результату

Результат виконання запиту після завантаження
демонстраційних даних командою npm run db:demo
26.11.2026.

| month | revenue | changeFromPreviousMonth |
|---|---:|---:|
| 2026-06-01 | 2694.93 | NULL |
| 2026-07-01 | 2048.95 | -645.98 |
| 2026-08-01 | 2176.47 | 127.52 |
| 2026-09-01 | 2612.47 | 436.00 |
| 2026-10-01 | 2040.44 | -572.03 |
| 2026-11-01 | 2223.47 | 183.03 |

### Аналіз результату

Найбільший обсяг продажів серед представлених
місяців спостерігається у червні — 2694.93.

У липні продажі зменшилися на 645.98.

Найбільше зростання відносно попереднього
представленого місяця відбулося у вересні — 436.00.

У жовтні спостерігається зниження на 572.03,
а в листопаді — зростання на 183.03.

Результати можуть використовуватися для аналізу
динаміки продажів, планування закупівель
та оцінювання ефективності роботи магазину.

### Особливості запиту

Місяці без нескасованих замовлень не потрапляють
до результату. Тому LAG порівнює поточний місяць
із попереднім місяцем, представленим у вибірці.

Запит враховує вартість усіх нескасованих
замовлень, а не лише фактично отримані платежі.

Дані поточного місяця можуть бути неповними.

## Тестування аналітичних запитів

Інтеграційні тести розташовані у файлі:

`tests/shop-analytics.test.ts`

Тести перевіряють:

- коректність обчислення виручки;
- формування топ-3 запчастин у кожній категорії;
- виключення скасованих замовлень;
- коректність групування продажів за місяцями;
- розрахунок зміни відносно попереднього місяця;
- повернення порожнього результату за відсутності даних.

Для запуску тестів використовується команда:

```bash
npx vitest run tests/shop-analytics.test.ts
```

У тестах використовуються заздалегідь визначені
набори даних та очікувані результати.

Усі 4 інтеграційні тести аналітичних запитів
успішно пройдено.

Демонстраційні результати можуть відрізнятися
залежно від дати генерації та стану бази даних.
